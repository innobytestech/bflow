# Configuration

## `bflow.yaml` and its layers

There are three layers; the last one wins:

1. **Global** (`~/.config/bflow/config.yaml`, on Windows `%AppData%\bflow\config.yaml`), with profiles shared across repositories.
2. **Profile**, which each repository references.
3. **Repo** (`bflow.yaml`), containing only what is specific to that repo.

`bflow init` creates `bflow.yaml`: it detects the stack, remote, base branch, and proposes check steps. It only asks what it could not detect; with `--yes` it asks nothing. Without `bflow.yaml`, bflow runs with the local tracker and git only.

```bash
bflow init [--yes] [--profile p] [--tracker local|plane|github] [--project P]
bflow doctor       # validates config, tools, connections, and hooks
```

### Profiles

```bash
bflow profile add acme --tracker plane --url https://plane.example.com --host github --base dev
bflow profile list
bflow profile use acme       # in this repo
```

```yaml
# global
profiles:
  acme:
    tracker: { adapter: plane, url: https://plane.example.com, workspace: acme }
    vcs: { host: github, base_branch: dev }
    agent: claude
```

```yaml
# repo bflow.yaml (generated by bflow init)
profile: acme
stack: go
tracker: { project: API }        # human-readable identifier, never UUID
check:
  steps:
    - { name: vet,   run: "go vet ./..." }
    - { name: test,  run: "go test -count=1 {race} ./..." }
    - { name: lint,  run: "golangci-lint run --new-from-rev={base}", needs: golangci-lint }
    - { name: vulns, run: "govulncheck ./...", needs: govulncheck, optional: true }
```

### Validation

Validation aggregates all problems into a single message, indicates line numbers for unknown fields, and rejects any key that resembles a secret.

## Check

`bflow check [ID]` runs the steps in `check.steps`, summarizes failures in a few lines, and links the result to a commit; full details remain in a file (`bflow show <ID> check`).

- `--quick <package>`: only fast steps on a package, for quick iterations. Does not record results, so it does not count toward reporting DONE.
- `check.test_step` (defaults to `test`): the step whose failure counts as reproducing a hotfix. Each `bflow check` with a task ID also saves its result per commit in `.bflow/tasks/<ID>/checks/<sha>.json` (not with uncommitted changes).
- `--verify`: does not run steps; verifies that the last check passed and corresponds to the current code (and that frozen tests have not changed).
- A step with `needs` depends on an external tool: if missing and the step is `optional: true`, it is skipped with a warning; if not optional, it fails.
- A vulnerability check step marks preexisting vulnerabilities untouched by the task as preexisting (see [guide](guide.md#when-something-gets-stuck)).

## Connecting a tracker

Tokens are validated before being saved to the system keychain (Credential Manager, Keychain, or Secret Service) and are never written to YAML. In CI, environment variables are used: `BFLOW_PLANE_TOKEN`, `GH_TOKEN`.

```bash
bflow connect plane --url https://plane.example.com --workspace my-workspace
bflow connect github --from-gh      # or --token
bflow tracker states                # how phases translate to your tracker states (read-only)
bflow tracker setup --dry-run       # which states are missing
bflow tracker setup                 # creates missing states
```

### Local tracker

The default: tasks are files in the repo, requiring no account or token. `bflow task add "title"` creates `LOCAL-1`, and `bflow task list` lists open tasks.

### Plane

`tracker.adapter: plane` with URL and workspace (from profile or `bflow.yaml`). Phases map to project states using literal names; `bflow tracker states` displays them and `bflow tracker setup` creates any missing states. New tasks begin in the backlog state; if the project lacks one, `bflow tracker setup` creates it.

### GitHub Issues and Projects

Tasks can live in the repository's issues (`GH-42` is issue #42), with or without Projects v2. Requires `vcs.host: github`; repo, API (`vcs.api_url`), and token are resolved from `bflow connect github`.

```yaml
vcs: { host: github }
tracker:
  adapter: github
  project: my-org/7        # optional; without it, phase is a label bflow:<phase>
  # prefix: GH             # task ID prefix (GH by default)
  # start_field: Start date  # Project date field where start time is stamped
```

- **Without project:** the phase is represented as a label `bflow:<phase>`. `bflow tracker setup` creates missing ones. An open issue without a label is backlog; a closed one is done. No start date is recorded.
- **With project:** the phase is an option in the single-select Status field, using the same names as Plane (`tracker.states` can customize them). `bflow tracker setup` adds missing options if the API preserves existing option IDs; otherwise, it writes nothing and prints instructions to add them manually (`create manually in project my-org/7, Status field:`). Upon start, the issue is added to the project and start date is stamped if the field exists.
- Reaching done closes the issue (bflow never reopens a closed issue) and the PR includes `Closes #N`.
- **Token:** the same token from `bflow connect github`. For organization Projects, a fine-grained token with organization Projects permission is required; for user Projects, a classic token with `project` scope. `bflow doctor` checks this.
- `bflow init` offers `github` when the remote is on GitHub and allows choosing a project (or none): `bflow init --tracker github --project owner/N`.

## Agents

`agent:` accepts a single tool (`agent: claude`) or a list (`agent: [claude, opencode]`); empty defaults to `claude`. `bflow init --agent claude,opencode` accepts multiple and detects `.opencode/`, `opencode.json`, and `opencode.jsonc`.

```bash
bflow render           # writes .claude/agents/bflow-<agent>.md; commit these files
bflow render --check   # in CI: fails if they do not match current configuration
```

Each agent has two layers. The **contract** with bflow (what it receives, what files it writes, what verdicts it can report and how) comes from the flow engine and is not configurable. The **craft** (how it does its work) provides sensible defaults that each repository can augment:

```yaml
# bflow.yaml
agents:
  implementer:
    model: sonnet
    effort: medium
    read: [docs/architecture/]           # agent reads these before starting
    extra: docs/bflow/implementer.md     # custom instructions copied into agent definition
  documenter: { model: haiku, effort: low }
```

With `read`, the agent does not load `CLAUDE.md` (`omit_claude_md: false` overrides this): repository rules reach it through those configured paths. A custom agent can be added to a phase in `flow.agents` and define its craft in `extra`; bflow prepends the contract. Generated agents use the `bflow-` prefix to avoid collisions with your own agents; `render` never overwrites a file it did not generate. If the repo contains `AGENTS.md` (read by Codex and OpenCode), `render` maintains a block explaining how to resume tasks with bflow. `bflow doctor` warns if agents are outdated or if an installed skill appears to handle process concerns (branches, PRs, trackers, specs), which might conflict with bflow; `doctor.ignore_skills` silences non-conflicting skills. More craft examples are in the [guide](guide.md#tuning-agents).

### Public surface and changelog

`flow.public_paths` lists repo paths that affect what end users see (commands, JSON, UI panels, config). If a diff touches them and the consumer-facing changelog was not modified, bflow rejects the documenter's DONE with `changelog_required`. Without this key, the gate is inactive.

```yaml
# bflow.yaml
flow:
  public_paths: [cmd/, internal/cli/, internal/config/config.go, "!*_test.go"]
```

An entry ending in `/` covers the directory; others are matched with `path.Match` (a pattern without `/` is also tested against the basename); `!` at the beginning negates/excludes. These must be repository paths: no `..`, absolute paths, or `.bflow/`. To exempt a task: `bflow unblock <ID> --no-changelog --note "reason"`.

### Narrative task comments

`report DONE` from implementer and documenter, as well as `bflow check --verify`, examine comment lines added by diff against base in `check.code_paths` (excluding `.md`). If any comment cites the task ID, `R<n>`, `T<n>`, `spec`, `according to`, `decision`, or `walkthrough`, DONE exits with code 2 and `narrative_comment`, and `--verify` with `not_verified`. A comment line starts with `//`, `#`, `/*`, `*`, `-- `, or `<!--`, or contains a trailing `//` outside quotes (`"`, `'`, or inline backticks). Compiler/preprocessor directives (`#include`, `#define`, `#pragma`…) do not count.

- `flow.comment_patterns`: list of regexes replacing fixed patterns. The task ID is always checked.
- `flow.narrative_comments: false`: disables this check. An empty list in `comment_patterns` does not disable it; it falls back to fixed patterns.

```yaml
# bflow.yaml
flow:
  comment_patterns: ['\bR\d+\b', '\bT\d+\b', '(?i)\bwalkthrough\b']  # omitting "spec" for OpenAPI YAMLs
  # narrative_comments: false                                        # or disable the rule
```

### Token budget and loop detection

`flow.budget` sets a new-token budget per phase. When a phase exceeds it, `bflow watch` highlights it in amber and the next command (`next`, `report`, etc.) prompts the `budget` gate: "Continue?". "Yes" continues, "Block" blocks the task with a note for the implementer. It does not abort work, but requests human confirmation.

```yaml
flow:
  budget:
    implementing: 200k          # 200,000 new tokens
    quality: 1.5M               # 1,500,000 new tokens
    # Values can be integers (200000) or with suffixes k/K (×1e3) or m/M (×1e6).
```

A phase without a budget specified in `flow.budget` produces no prompt. Up to 1×, 2×, 3× the budget, the gate is prompted at each multiple. After answering "No" at a multiple, the next multiple asks again.

`flow.loop_repeats` detects when a subagent repeats identical actions (Bash, Read, Edit, Write with identical input). On the Nth identical repetition, guard rejects it and `bflow watch` displays the detected loop. Any permitted Edit or Write resets the Bash and Read counters (to allow re-running test suites after changes). `0` disables loop detection; `2` stops at the second repetition.

```yaml
flow:
  loop_repeats: 2              # Stops on second identical repetition (0 = disabled).
```

## Claude Code and OpenCode

### Claude Code

`bflow install claude` installs the skill and hooks (see [installation](installation.md#installing-in-your-agent-tool)). The skill is around 30 lines: it contains no flow rules, only how to interpret `next`. The hooks execute:

- `bflow hook session-start` when opening a session.
- `bflow guard --reads` before each edit, command, or `Read` (only logging reviewer `Read`s during quality, to measure diff coverage).
- `bflow hook tokens` when ending each turn and subagent (each tracks its own transcript).
- `bflow hook subagent-stop` when a bflow agent finishes: if it did not report, nudges it up to 2 times with what is missing, then blocks the task for human decision.
- `bflow statusline`, the status bar:

```
API-12 · implementing · 1h42m · round 1 · 145.1k new · 2.9M cache
```

Source files are located in [`adapters/claude/`](../../adapters/claude/README.en.md).

### OpenCode

With `opencode` under `agent:`, `bflow render` writes `.opencode/agents/bflow-<agent>.md` (subagents with `edit` and `bash` permissions based on each agent's scope) and `bflow render --check` covers both sets. It also writes `.opencode/plugins/bflow.js` (OpenCode 1.x) and `.opencode/plugins/bflow2/` (OpenCode 2.x, which injects task state into the initial prompt); these are committed and not edited manually: guard runs before bash, edit, write, and patch, and tracks tokens by phase and agent. OpenCode lacks subagent nudging; the plugin injects `bflow hook session-start` on root session creation (without requiring an answer), so `/clear` preserves task context.

OpenCode expects models as `provider/model`, so agent aliases (`opus`, `sonnet`, `haiku`) are mapped with `models.opencode`. Defaults are `opus` for spec-author and reviewer, `sonnet` for implementer, security-auditor, and ux-auditor, and `haiku` for scout and documenter; `agents.<name>.model` overrides them. There are two places with different scopes:

- `bflow.yaml` (team): model written to `model:` in versioned agents.

```yaml
models:
  opencode:
    opus: anthropic/claude-opus-4
    sonnet: anthropic/claude-sonnet-4
    haiku: anthropic/claude-haiku-4
```

- `models:` at top level of global configuration (personal only; not versioned in this repo, mapped via `models: { opencode: { opus: <provider/model>, ... } }`): never written to repository files. `bflow render` and `install opencode` apply this to `agent.bflow-<agent>.model` in your `opencode.json` (`$XDG_CONFIG_HOME/opencode` or `~/.config/opencode`), preserving other settings. If the repo defines the alias, repo settings win and no override is written. If only `opencode.jsonc` exists or `opencode.json` cannot be read, bflow will not edit it: `render` outputs the `{"agent": ...}` JSON block to paste. `render --check` neither reads nor writes your `opencode.json`.
- `models` in a profile are ignored (`render` and `doctor` will warn): place them in `bflow.yaml` or global configuration top-level.

Each `start` logs the model of each agent. `bflow stats` (under `models:` and `data.models`) and `bflow doctor` (`model-verdict` check) compare the 3 most recent tasks under current configuration against the previous 3: gate rejections, rounds, and hotfixes. If metrics degrade, it warns in red and indicates previous model to revert to; to revert, update `bflow.yaml` (`agents`) and run `bflow render`. bflow never reverts automatically.

Values containing `/` are used verbatim. An alias without an equivalent in either configuration leaves the agent without `model:` (falling back to your OpenCode default) and `render` and `bflow doctor` issue a warning; `doctor` also warns if your `opencode.json` is out of date (`bflow render`). Source files are located in `adapters/opencode/`.

## Panels and notifications

- `bflow watch` is a live terminal dashboard: who is working and since when, pending human gates, next step, time per phase, tokens per agent, friction, and recent events. `bflow watch --open` opens it in another tab or window if not already running. With `ui: { watch: true }`, `bflow start` opens it automatically (never in CI or headless environments).
- `bflow ui` provides a read-only browser UI: kanban board, lane roadmap, metrics, and all repositories grouped by profile. With `ui: { web: true }`, the browser opens automatically upon task start; if already open, it does not open a duplicate.
- When a task awaits a human decision (gate or blocked state) and Claude ends its turn, bflow sends a system notification once per waiting state. `ui: { notify: false }` disables this.

As these represent personal preferences, `ui:` belongs in global configuration, not `bflow.yaml`. The initial `bflow init` on a machine asks what to open (terminal and browser, terminal only, or none) and persists it there. You can customize it at any time by editing `ui:`.
